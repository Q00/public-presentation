섹션 전환 / 학습 목표

4-1의 도입은 curriculum.md rows 38-40의 세 클립을 그대로 따른다. 큰 일을 작은 일로 자르는 기준, 완료조건 트리, 작업 트리 다이어그램 실습을 하나의 학습 흐름으로 묶는다.

학습 목표는 보조 세션 수를 늘리는 것이 아니라, 보조 세션이 추측 없이 시작하고 검수자가 같은 기준으로 끝났다고 말할 수 있는 작업 단위를 만드는 것이다.

용어는 네 개만 고정한다. 작업 트리는 부모 목표와 자식 리프의 관계이고, 리프 태스크는 목적·입력·범위·완료조건이 닫힌 실행 단위다. 완료조건은 검수자가 확인할 문장이고, handoff는 4-2에서 세션 사이에 남길 전달 형식이다.

문제상황

  • 이 슬라이드는 4-1의 출발 문제를 잡는다. 큰 일을 그대로 넘기면 보조 세션은 입력, 범위, 완료조건을 추측하게 된다.
  • curriculum.md의 핵심인 "한 번에 끝낼 수 있는 크기로 쪼갠다"는 말은 작업을 작게 만드는 미화가 아니라 추측을 제거하는 설계 규칙이다.
  • 강의에서는 네 가지 실패를 차례대로 말한다. 첫째, 목표 흐림. 둘째, 입력 추측. 셋째, 범위 확장. 넷째, 완료조건 누락이다.
  • 여기서 목표는 새로운 전략 목표가 아니라 부모 노드와 리프 태스크가 연결되어 있는지 보는 기준이다. 부모와 연결되지 않으면 작업 트리가 아니라 별도 요청 목록이 된다.
  • interview.md의 하네스 비유는 여기서 보충 맥락으로만 쓴다. 힘이 큰 여러 세션을 쓰려면 먼저 어디로 가야 하는지와 어디서 멈출지를 구조로 정해야 한다.
  • 전환 멘트: 그래서 리프 태스크는 "작은 일"이 아니라 "추측하지 않아도 시작하고 끝낼 수 있는 일"이어야 한다.

  • 종료는 handoff만 읽고 다음 세션의 첫 행동이 보일 때다. 여기서는 완료 handoff, 결과 요약, 다음 행동을 남긴다.
  • 재작업은 기준은 충분하지만 결과가 기준을 만족하지 못한 상태다. 수정 지시, 미충족 조건, 재검수 기준이 남아야 생성 세션이 같은 실수를 반복하지 않는다.
  • 재질문은 기준 자체가 불충분한 상태다. 검수 기준, 남은 질문, 금지사항이 애매하면 재작업이 아니라 질문 목록과 확인할 결정을 남긴다.

Case Study 역할

진행 시간 cue: 4:00-7:00. 1분은 case study의 목적과 guardrail, 1분은 repo 경계 관찰, 1분은 수강생 다이어그램으로 번역하는 예시에 쓴다.

oh-my-claudecode는 분업형 하네스의 레퍼런스다. README의 팀 분업 흐름은 작업을 계획, 명세, 실행, 검증, 수정 루프로 나누고, repo 구조는 agents, skills, src/team, bridge가 각기 다른 책임을 갖도록 나뉘어 있다.

이 case study의 연결점은 curriculum.md의 핵심 문장인 "서브 에이전트로 메인 세션 컨텍스트를 지키는 법"이다. oh-my-claudecode를 볼 때는 기능 목록보다 메인 세션에 남길 상태, 보조 세션에 넘길 작업, handoff로 되돌릴 결과가 어떤 파일 경계로 분리되는지를 먼저 본다.

레퍼런스 repo: https://github.com/yeachan-heo/oh-my-claudecode. 설치나 실행 검증은 하지 않고 구조 관찰만 한다.

핵심개념: 세 가지 경계

  • 역할 경계: planner, executor, verifier, code-reviewer처럼 책임 이름이 갈라지는 지점을 본다. 수강생 산출물에서는 이 경계를 질문 리프, 생성 리프, 검수 리프, 통합 리프로 번역한다.
  • 기억 경계: 메인 세션에 남길 상태판과 보조 세션에서 버려도 되는 대화 흐름을 구분한다. 수강생 산출물에서는 목표, 현재 상태, 남은 위험, 다음 결정만 메인에 남기고 시행착오 전문은 handoff로 압축한다.
  • handoff 경계: inbox/outbox와 merge 관련 경로는 결과를 바로 섞지 않고 회수하는 관찰 지점이다. 수강생 산출물에서는 결과 요약, 완료조건 충족 여부, 남은 질문, 다음 행동을 handoff 필드로 남긴다.

구체 예시로 agents/planner.md와 agents/executor.md를 보여줄 때는 "이 repo가 이렇게 실행된다"가 아니라 "계획 책임과 실행 책임을 한 문서에 섞지 않는 구조를 관찰한다"라고 말한다. 그 다음 곧바로 수강생 프로젝트의 리프 태스크 표에서 계획 리프와 생성 리프를 분리하게 한다.

oh-my-claudecode 설계 포인트

  • 팀 분업 흐름은 하나의 긴 대화가 아니라 계획 → 명세 → 실행 → 검증 → 수정으로 이어지는 단계형 오케스트레이션 표면으로 읽는다. 메인 세션은 목표, 상태, 다음 결정을 붙잡고 단계별 작업은 분리된 실행 단위로 넘긴다.
  • agents/는 만능 보조자가 아니라 planner, executor, verifier, code-reviewer처럼 책임이 좁은 역할 문서다. 설계 포인트는 에이전트를 많이 두는 것이 아니라 서로 겹치지 않는 완료조건을 갖게 하는 것이다.
  • skills/는 세션 안에서 반복 호출할 수 있는 작업 표면이다. 학습자는 스킬을 "기억을 보존하는 곳"이 아니라 정해진 절차를 다시 실행하게 만드는 진입점으로 본다.
  • src/team/의 phase, role, task, queue 관련 파일은 프롬프트 안의 약속을 실행 제어 코드로 옮기는 경계다. 작업 분해 하네스에서는 이 경계를 문서형 규칙, handoff 양식, 검수표로 먼저 흉내 낸다.
  • inbox/outbox와 merge 관련 경로는 보조 실행 결과를 바로 메인 세션에 섞지 않고 handoff로 받은 뒤 취합하는 구조를 보여준다. 관찰 목표는 "어떤 결과가 언제 리더에게 돌아오는가"를 표시하는 것이다.
  • bridge/와 실행 연결 경로는 세션 안 호출, MCP 연결, 터미널 보조 실행을 분리한다. 이 분리는 런타임이 바뀌어도 역할 문서와 handoff 규칙을 그대로 유지하기 위한 장치로 설명한다.

실습 절차 / 체크포인트

이 슬라이드는 4-1의 작업 트리 기준을 4-4 프로젝트 입력에 적용한 뒤, 4-2 세션 분리와 4-3 검수 루프까지 연결하는 사례다. 기획문서를 바로 실행시키지 않고, 먼저 작업 단위를 닫고, 병렬 실행 가능한 리프를 나누고, handoff로 통합한 뒤 3단 검수 판정으로 피드백 루프를 만든다.

scenario demo는 3장에서 만든 1페이지 기획문서를 입력으로 둔다. 강사는 "기능 후보를 구현해줘"라는 큰 요청을 바로 실행하지 않고, oh-my-claudecode에서 관찰한 역할·라우팅·handoff 경계를 수업용 작업분해 흐름으로 번역한다. 이때 repo를 실행하거나 성능을 주장하지 않고, agents/, src/team/, inbox/outbox, merge 관련 파일명을 관찰 렌즈로만 사용한다.

  • 실습 목표: 문서를 할 일로 쪼개고, 병행/대기 작업을 나누기.
  • 수행 절차 1: 기획문서에서 목표, 사용자, 기능, 제약, 성공 기준을 뽑는다.
  • 수행 절차 2: 역할 분리부터 적는다. 메인 세션은 목표, 현재 상태, 남은 결정만 들고 질문 세션은 모호함, 생성 세션은 산출물, 검수 세션은 통과·재작업·재질문 판정을 맡는다.
  • 수행 절차 3: 각 항목을 작업 트리의 리프 태스크로 변환하고 목적, 입력, 범위, 완료조건이 닫힌 작업 단위인지 확인한다.
  • 수행 절차 4: 리프 태스크마다 입력/출력 계약을 설계한다. 입력 계약에는 기획문서 필드와 금지사항을, 출력 계약에는 산출물, 완료조건, 검수 판정, 남은 질문을 넣는다.
  • 수행 절차 5: 리프 태스크마다 우선순위, 선행조건, 병행 가능 여부, 검수 세션을 표시한다.
  • 수행 절차 6: 4-2 세션 분리 설계의 질문/생성/검수 역할과 handoff 양식을 각 리프에 연결한다.
  • 수행 절차 7: 병렬 실행은 선행조건이 닫힌 리프에만 허용한다. 같은 입력을 읽어도 서로 다른 산출물을 내는 작업은 병렬로 보내고, 한 리프의 결과가 다른 리프의 입력이 되면 대기 작업으로 표시한다.
  • 수행 절차 8: 통합 단계에서 메인 세션은 보조 세션의 대화 전문을 합치지 않는다. 각 세션의 handoff, 결과 요약, 남은 질문, 완료조건 충족 여부만 상태판에 취합한다.
  • 수행 절차 9: 4-3 검수표로 형식, 의미, 목적을 분리해 검증한다. 형식은 필수 칸과 포맷, 의미는 요구사항 반영과 모순, 목적은 다음 업무 진행 가능성을 본다.
  • 수행 절차 10: 피드백 루프는 판정으로 닫는다. 통과는 다음 리프로 이동, 재작업은 생성 세션에 수정 handoff 전달, 재질문은 질문 세션으로 회수, 종료는 중단 사유를 남긴다.
  • demo step 1: agents/planner.md 관찰 렌즈로 기획문서의 모호한 결정을 먼저 표시한다. 수업 번역은 "질문 세션으로 되돌릴 리프"와 "바로 생성해도 되는 리프"를 분리하는 것이다.
  • demo step 2: src/team/task-router.ts와 src/team/dispatch-queue.ts 관찰 렌즈로 리프의 선행조건과 대기열을 표시한다. 수업 번역은 "같은 입력에서 독립 산출물을 만드는 리프만 병렬 후보"라는 판단이다.
  • demo step 3: src/team/inbox-outbox.ts, src/team/outbox-reader.ts, src/team/merge-coordinator.ts 관찰 렌즈로 결과 회수와 통합 판정을 설명한다. 수업 번역은 대화 전문을 합치지 않고 handoff, 결과 요약, 남은 질문, 3단 검수 판정만 상태판에 남기는 것이다.
  • 작업분해 실행 루프 사용법: 루트에는 기획문서 입력을 두고, 가운데에는 planner lens와 router lens를 둔다. 오른쪽 리프에는 dispatch, outbox, merge, loop가 순서대로 보이도록 표시한다.
  • 체크포인트: 산출물 이름은 작업 분해 설계도이며, 한 태스크가 어떤 입력으로 시작해 어떤 출력과 판정으로 끝나는지 명확해야 한다.
  • 완료 확인 체크포인트: 작업 분해 설계도에 역할 분리, 닫힌 리프 태스크, 입력/출력 계약, 우선순위, 선행조건, 병행 가능 여부, 4-2 세션 배정과 handoff 책임, 4-3 검증 판정과 피드백 루프가 들어 있으면 실습 완료로 본다.

실습 절차 / 체크포인트

실제 적용 시나리오는 3장에서 만든 1페이지 기획문서를 받아 개발 실행 전에 작업 목록, 우선순위, 병행/대기 관계, handoff, 3단 검수 기준으로 바꾸는 것이다. 이 프로젝트에서는 새 외부 사례를 만들지 않고, curriculum.md의 "기획문서 → 작업분해" 흐름과 앞선 4-1, 4-2, 4-3 산출물을 하나로 묶는다. 특히 4-4에서는 4-2~4-3 적용 사례로 병렬 실행, 통합, 검증, 피드백 루프가 한 흐름으로 닫히는지 확인한다.

project demo는 세 장면으로 진행한다. 첫 장면은 입력 기획문서에서 리프와 대기 질문을 뽑는 장면, 둘째 장면은 병렬 후보를 handoff로 보내고 상태판에는 요약만 남기는 장면, 셋째 장면은 검수 결과를 통과·재작업·재질문으로 되돌리는 장면이다. 각 장면은 oh-my-claudecode의 observable path를 수업용 구조 언어로 번역하는 방식으로 설명한다.

  • 실습 목표: 개발 실행형으로 넘어가는 분업형 하네스를 완성한다. 메인 세션에는 목표, 현재 상태, 남은 위험, 다음 결정만 남기고, 질문·생성·검수 보조 세션이 닫힌 리프 태스크를 처리하게 한다.
  • 수행 절차 1: 입력으로 받을 기획문서의 필수 항목을 목표, 사용자, 기능, 제약, 성공 기준으로 고정한다.

  • 수행 절차 3: 4-2 handoff 양식으로 각 리프에 담당 세션, 입력, 산출물, 금지사항, 남은 질문을 붙인다. 선행조건이 없는 리프는 병렬 실행 후보로 표시하고, 다른 리프 결과를 기다리는 일은 대기 작업으로 둔다.
  • 수행 절차 4: 병렬 실행 결과는 메인 세션에서 통합한다. 통합 기준은 산출물 전문이 아니라 handoff, 결과 요약, 완료조건 충족 여부, 충돌 여부, 남은 질문이다.

4-4의 적용 결과는 3장에서 만든 1페이지 기획문서를 개발 실행 직전의 분업형 하네스로 바꾸는 것이다. 결과물은 단순 작업 목록이 아니라 프로젝트 2 · 작업분해 하네스 v1이며, 그 안에는 리프 태스크, 우선순위, 선행조건, 병행/대기 표시, 세션 배정, handoff 양식, 3단 검수표, 피드백 루프가 함께 있어야 한다.

실패 / 개선 포인트

  • 실패 1: 리프 태스크가 목적, 입력, 범위, 완료조건으로 닫히지 않아 보조 세션이 추측한다. 개선: 4-1 작업 트리 기준으로 한 번에 끝낼 수 있는 단위까지 다시 쪼갠다.
  • 실패 2: 보조 세션의 대화 전문을 메인 세션에 합쳐 컨텍스트를 다시 무겁게 만든다. 개선: 4-2 기준에 따라 세션은 버리고 handoff, 결과 요약, 남은 질문만 상태판에 남긴다.
  • 실패 3: 병렬 실행 가능 여부를 선행조건이 아니라 급한 정도로만 판단한다. 개선: 각 리프에 선행조건과 병행/대기 표시를 붙이고, 충돌 가능성이 있는 작업은 통합 순서를 먼저 정한다.
  • 실패 4: 검수가 문장과 포맷만 보고 실제 업무 사용 가능성을 보지 않는다. 개선: 4-3 검수표로 형식, 의미, 목적을 분리하고 통과, 재작업, 재질문, 종료 판정을 다음 행동에 연결한다.

  • 입력 체크: 기획문서에 목표, 사용자, 기능, 제약, 성공 기준이 있고 애매한 항목은 질문 세션으로 회수되어 있는가.
  • 작업 체크: 모든 리프 태스크가 목적, 입력, 범위, 금지사항, 완료조건, 산출물을 갖고 있는가.
  • 분업 체크: 메인 세션은 상태판과 다음 결정만 들고, 질문·생성·검수 세션은 각각 닫힌 책임만 맡는가.
  • 병렬 체크: 선행조건이 없는 작업만 병렬 실행 후보이며, 대기 작업은 어떤 결과를 기다리는지 적혀 있는가.
  • 통합 체크: 통합 기준이 산출물 전문이 아니라 handoff, 결과 요약, 완료조건 충족 여부, 충돌 여부, 남은 질문으로 정의되어 있는가.
  • 검수 체크: 형식, 의미, 목적 검수가 분리되어 있고 판정이 통과, 재작업, 재질문, 종료 중 하나로 닫히는가.
