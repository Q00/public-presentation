진행 메모

  • curriculum.md 핵심 문장: 사람 마음대로 어겨지는 흐름은 코드로 잠근다.
  • 이 슬라이드는 목표와 문제상황을 같이 잡는다. 목표는 MCP를 권장하는 것이 아니라, 문서형과 분업형으로 충분한 업무를 먼저 걸러내는 것이다.
  • 문서형 하네스는 규칙과 출력 형식을 고정하고, 분업형 하네스는 메인 세션의 맥락 소모를 줄인다. 하지만 어떤 단계를 반드시 먼저 해야 한다는 제약은 사람이 계속 지켜야 한다.

  • Ouroboros의 event store와 rewind는 이 구조를 설명하는 참고 언어다. event store는 결정과 실패 이력을 남기는 관찰 지점, rewind는 돌아갈 체크포인트를 설명하는 관찰 지점으로만 다룬다.
  • 전환 멘트: 상태 계약이 있으면 실패를 한 종류로 뭉개지 않고 재시도와 재질문을 나눌 수 있다.

  • 운영 기록은 결과물 자체보다 운영을 가능하게 하는 정보다. 완료한 이유, 실패한 이유, 돌아갈 체크포인트, 사람에게 물을 질문을 남겨야 다음 실행이 같은 판단을 반복하지 않는다.
  • Ouroboros 관찰 언어로 바꾸면 Seed와 AC Tree는 완료 신호의 기준, evaluate는 실패 유형의 발견, event store는 운영 기록, rewind는 재시도할 체크포인트다. 이 연결은 구조 관찰이지 실행 보장이 아니다.
  • 강사 질문: "여러분의 MCP 설계 초안에서 완료 신호가 가장 모호한 단계는 어디인가요?", "그 모호함은 재시도로 해결되나요, 사람에게 다시 물어야 하나요?"

문제상황 해설 확장

  • 흐름 단절은 가장 흔한 실패다. 인터뷰에서 나온 결정이 명세에 반영되지 않고, 명세의 성공 기준이 작업 지시로 내려가지 않고, 작업 결과가 검수 기준과 연결되지 않으면 사람은 매 단계마다 다시 설명해야 한다.
  • 상태 부재는 반복 실행에서 드러난다. 왜 이 결정을 했는지, 어느 실패에서 되돌아왔는지, 다음 실행에서 무엇을 재사용해야 하는지가 남지 않으면 하네스는 자동화가 아니라 기억력 테스트가 된다.
  • 검수 약화는 데모 단계에서 드러난다. 결과물이 있어도 완료 기준이 붙어 있지 않으면 "좋아 보인다"와 "쓸 수 있다"를 구분할 수 없고, 5-3에서 만든 stop rule도 적용할 위치를 잃는다.
  • 그래서 이 슬라이드의 핵심은 프롬프트 품질 비판이 아니다. 좋은 프롬프트라도 다음 단계의 입력, 상태 기록, 검수 기준, 복귀 지점으로 연결되지 않으면 최종 하네스가 되지 않는다는 점을 설명한다.

Ouroboros로 넘어가는 연결 멘트

  • Ouroboros를 보는 이유는 레퍼런스 자체를 소개하기 위해서가 아니다. interview → Seed → execute → evaluate → evolve가 하나의 관측 가능한 흐름으로 이어질 때, 방금 본 네 가지 문제가 어떻게 줄어드는지 확인하기 위해서다.
  • Seed와 AC Tree는 흐름 단절을 줄이는 관찰 지점이다. event store와 checkpoints, rewind는 상태 부재를 줄이는 관찰 지점이다. evaluate와 evolve는 검수 약화와 무한 반복을 분리해서 보는 관찰 지점이다.
  • 이 연결은 source-fidelity guardrail 안에서만 말한다. 설치, 실행 성공, 성능, 채택 규모, 별점 같은 주장은 하지 않고, curriculum.md rows 59-61과 interview.md가 허용한 구조 언어에 머문다.

Ouroboros MCP 하네스 아키텍처 설계 포인트

  • 아키텍처의 중심은 interview → seed → execute → evaluate → evolve를 정해진 순서로 통과시키는 전체 연결 파이프라인이다. 좋은 프롬프트를 이어 붙인 것이 아니라, 각 단계의 입력, 산출물, 다음 단계 진입 조건을 코드형 경계로 둔다.
  • src/ouroboros/bigbang/과 Seed 관련 흐름은 입력 정제층이다. Socratic Interview로 사람의 암묵지를 꺼내고, Seed와 AC Tree로 실행 가능한 데이터 구조와 검수 단위를 만든다.
  • src/ouroboros/execution/과 src/ouroboros/evaluation/은 실행과 검수를 분리하는 검수 경계이다. 실행 결과가 바로 완료로 처리되지 않고 검수 단계별 평가 게이트를 거쳐 종료, 재시도, 재질문으로 갈라진다.
  • src/ouroboros/evolution/과 src/ouroboros/persistence/는 반복을 추적 가능한 반복 추적 경계로 바꾼다. Wonder/Reflect 재정의 흐름, convergence detection, event store, checkpoints, rewind가 있어 같은 실패를 반복하지 않고 이전 결정 지점으로 돌아갈 수 있다.
  • src/ouroboros/mcp/는 외부 도구 호출의 의미와 진입점을 제한하는 도구 호출 경계이고, src/ouroboros/orchestrator/는 Claude Code, Codex CLI 같은 런타임 차이를 흡수하는 실행 환경 경계다. 학습자는 도구 호출 자체보다 호출 전 조건, 상태 기록, 실패 후 복귀 지점이 어디에 남는지 본다.

  • execute와 review는 작업과 검수를 분리한다. operate는 종료, 재시도, 재질문, 복귀 지점을 운영 가이드로 남긴다.
  • Ouroboros 관찰은 이 구조를 이해하기 위한 참고다. 수강생 결과물은 자기 업무용 최종 하네스와 운영 가이드다.

핵심개념 단계별 해설

  • interview 단계의 책임은 답변을 많이 모으는 것이 아니라 모호한 자리를 줄이는 것이다. 수강생은 업무 목표, 금지 조건, 입력 자료, 완료 기준, 예외 상황을 질문으로 끌어내고 다음 단계가 사용할 결정 목록으로 남긴다.
  • seed / spec 단계의 책임은 그 결정을 실행 가능한 입력으로 고정하는 것이다. 여기서 목표, 제약, 성공 기준이 흐릿하면 execute 단계가 다시 추측하게 되므로, 2장의 Define 고정과 5-2의 안/밖 경계를 다시 연결한다.
  • execute / review 단계의 책임은 만드는 일과 판정하는 일을 섞지 않는 것이다. 작업자는 작은 단위의 산출물을 만들고, review는 AC Tree나 체크리스트처럼 분리된 기준으로 종료, 재시도, 재질문을 가른다.
  • operate 단계의 책임은 한 번의 성공을 다음 실행의 자산으로 바꾸는 것이다. 결정, 실패 사유, 되돌아갈 지점, 다음 질문을 운영 가이드에 남겨야 하며, 이 지점에서 event store와 rewind가 관찰 언어로 다시 연결된다.

Ouroboros 앵커와 수강생 산출물의 차이

  • Ouroboros의 interview → Seed → execute → evaluate → evolve 흐름은 전체 연결 파이프라인을 설명하는 기준점이다. 하지만 수강생이 제출하는 것은 Ouroboros 구조도 복사본이 아니라 자기 업무의 최종 하네스 설계도다.
  • Seed는 "내 업무에서 AI가 추측하면 안 되는 실행 입력"으로 번역한다. AC Tree는 "작업 결과를 작게 나누어 판정하는 기준"으로 번역한다. event store와 rewind는 "다음 실행에서 재사용할 운영 기록과 복귀 지점"으로 번역한다.
  • 강의 중에는 네 카드가 서로 이어지는 순서를 계속 강조한다. interview 없이 seed를 쓰면 입력이 빈약하고, seed 없이 execute를 시작하면 추측이 늘고, review 없이 operate로 넘어가면 운영 가이드가 근거 없는 회고록이 된다.
